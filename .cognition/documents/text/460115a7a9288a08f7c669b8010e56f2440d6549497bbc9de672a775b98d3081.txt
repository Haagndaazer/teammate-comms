## Headline
teammate-comms is a much smaller port than vibe-cognition: message store, registry, groups, reactions, profiles, dashboard, broker CLI are file-based and harness-neutral. Exactly ONE thing is Claude-specific in a load-bearing way — the idle wake (notifications/claude/channel) — plus cosmetic Claude-isms (spawn command, env-var names, skill/tool text, launch flags).

Codex has no MCP channel equivalent; upstream requests are open with no maintainer response (#15299 Mar 2026, #20312 Apr 2026, #35542 Jul 2026). But since codex-cli 0.149.0 (2026-08-20) Codex ships a durable cross-process user-message queue with an idle-dispatch watcher: `codex queue --thread <uuid> --message <text>` (app-server method thread/queue/add) [src][bin]. A queued message on an idle thread starts a new turn; on a busy thread it waits and becomes the next user turn — never dropped [src]. Strictly better than the Claude channel (which Claude Code drops, GH #38736/#61797). Wake regime: Claude Code instance → channel push (unchanged); Codex instance → the recipient's OWN watcher thread runs `codex queue` against its own thread id. The sender never needs to know the recipient's harness; the inbox file is the only shared contract. Cross-harness messaging needs zero protocol changes — a Claude agent and a Codex agent on the same machine already share ~/.claude/TeammateComms.

Two new design pieces: (1) the server must learn its own Codex thread id (Codex gives the MCP child no session/thread env); (2) Claude-only env handoffs (TEAMMATE_AGENT, CLAUDE_PROJECT_DIR) need a Codex path because Codex's MCP child env is an allowlist.

## 4.1 Wake on Codex = self-queue via codex queue (source-verified)
(1) codex queue resolves the target then calls thread/queue/add; via the daemon if running, else the CLI starts an embedded app-server in its own process; either way the item is written to durable $CODEX_HOME/queue_1.sqlite (present on this machine [live]). require_thread accepts a thread NOT loaded in the calling process if it exists in the thread store and is not archived / not an unloaded spawned sub-agent. (2) The plain interactive TUI runs an in-process app-server (AppServerTarget::Embedded, tui/src/startup_orchestration.rs) and installs the queue extension (app-server/src/extensions.rs; message_processor.rs constructs queue_service whenever a state DB opened AND experimental_thread_store is Local, the default — an in-memory thread store silently disables queue wakes) — runs QueuedItemService::watch_external_messages: a 10 s poll of the queue DB's change_version; on change emits ThreadQueueChanged and, if AgentStatus is not Running/Interrupted/Shutdown/NotFound, calls wake_if_loaded → emit_thread_idle_lifecycle_if_idle → on_thread_idle → dispatch_if_idle → a NEW TURN with the queued text as the user message; if a turn is in flight it stays queued and dispatches on next idle. (3) Same-process adds wake immediately; cross-process within ≤10 s.
Consequences for channel.py: keep all gating logic; only the emit changes — on Codex run [codex, queue, --thread, <thread_id>, --message, <same signal-only content>] as list-argv subprocess with DEVNULL stdio from the watcher thread. Disable re-nudge on Codex. Queued text is a USER TURN, keep it signal-only ending with the teammate_inbox instruction. codex must be on PATH for the server (Codex MCP child env includes PATH [vc]).
Rejected: write queue_1.sqlite directly (private, versioned, migrator-owned schema); speak JSON-RPC to the daemon socket ourselves (daemon not default; experimental opt-in); Stop hook block loop (turn-end only; #37937 trap); async hooks (cannot start a turn [doc]); WezTerm keystroke injection (fallback only); wait for upstream (no engagement in 3–6 months).

## 4.2 Learning the Codex thread id (and project dir)
codex queue needs the thread UUID (no --session-name flag in 0.153.4 [bin]; names via /rename or thread/name/set, must be unique). Ordinary tool calls carrying _meta.threadId is an unproven spike item [vc]. The SessionStart hook payload's session_id IS a thread id (SessionStartRequest.session_id: ThreadId in codex-rs/hooks/src/events/session_start.rs, populated from sess.session_id() in codex-rs/core/src/hook_runtime.rs [src]); hooks also receive cwd [doc]. Caveat: session_id() is the ROOT thread's id — equals the thread's own id for a top-level interactive session or independently launched process (our cases), NOT for a Codex-native spawned sub-agent or fork; never reuse this handoff for those.
Recommended handoff: the SessionStart hook (all sources) emits additionalContext "teammate-comms: harness=codex thread_id=<session_id> project_dir=<cwd>"; the agent passes these to teammate_register (new optional args harness_session, project_dir); register record stores harness + harness_session; teammate_list/profile show the harness. Fallbacks: (a) _meta.threadId if present; (b) hook writes ${PLUGIN_DATA}/sessions/<session_id>.json + parent-pid correlation; (c) session_index.jsonl most-recent-by-cwd (last resort). Harness detection: params.clientInfo.name on initialize (spike records exact strings) with TEAMMATE_HARNESS env override.

## 4.3 Spawning a Codex teammate
Per-spawn env cannot reach a Codex MCP child. Launch codex -C <project_dir> [bypass flags] "<prompt>" where the prompt carries identity ("You are teammate <agent>; call teammate_register(agent=...) first"); TEAMMATE_SPAWNED_BY becomes a register arg; a harness argument on teammate_reincarnate picks the builder; spike confirms which bypass flags a DEVNULL child needs.
